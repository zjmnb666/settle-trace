# SettleTrace · Agent 工具设计 v1

> 目标：把"固定流程问答"升级为**会自主决策的核对智能体**——但只在"怎么取证、怎么归类疑点"上自主，
> 不在"能不能出结论、能不能确认"上自主。
>
> 状态：已实现并通过真实模型端到端验证（2026-11-05）。代码位置 `project/app/core/agent/`。

---

## 一、先纠正一处对应关系

报销助手模板里的 `create_draft`（建报销单草稿）在本项目**没有对应物**：本系统不产生单据，
也没有"申请—审批"这条业务链。最接近的实体是「核对结论草稿」（`review_draft`），它是
**一堆带来源定位的建议 + 疑点清单**，状态只有 `draft / needs_review / superseded`。

所以顺序约束不是"校验通过才能建单"，而是：

> 证据齐 → 映射过 → 比对过 → 才能出草稿；草稿里必须挂着未决疑点，且永远不能自己变成"已确认"。

`review_draft.status` 的 CHECK 约束里**根本没有 confirmed 这个值**——任何代码都不可能把它写成已确认。
这是"人工闸口"最省力也最可靠的实现方式：不是拦住，而是让它不存在。

## 二、8 个工具（Function Calling 规范）

| # | 工具 | 层 | 作用 | 落库 | 前置条件 |
|---|---|---|---|---|---|
| 1 | `search_corpus` | L0 读 | 检索结算口径/合同条款 | 否 | — |
| 2 | `get_settlement` | L0 读 | 单据头 + 版本列表（版本 id 命名为 `version_id`） | 否 | — |
| 3 | `list_fee_lines` | L0 读 | 当前有效版本下的全部费用行 | 否 | 已 `get_settlement` |
| 4 | `get_evidence` | L0 读 | **批量**取证据（文件/页码/字符区间/字段/原文） | 否 | 有真实 `fee_line_id` |
| 5 | `map_service_item` | L1 分析 | **批量**费用名称 → Top3 合同服务项 + 置信度 + `need_human` | 否 | 同上 |
| 6 | `check_duplicates` | L1 分析 | 整单查重（跨币种先按汇率折算），只给高/中/低 + 依据链 | 否 | 行已加载 |
| 7 | `record_finding` | L2 写 | 登记发现/疑点 | **是** | `evidence_refs` 非空 |
| 8 | `build_review_draft` | L2 写 | 汇总核对草稿 | **是** | 见 §3 闸口 |
| 9 | `escalate_to_human` | L2 写 | 转人工（逃生门） | **是** | 任何时候可调 |

**唯一 skill：`review_settlement(no)`** —— 由系统提示词给出的固定作业顺序 + 闸口共同约束，
不让模型自由编排 9 个工具。理由见 §5。

### 刻意不提供的工具

`pay` · `issue_invoice` · `confirm_settlement` · `approve` · `delete_duplicate`

不是"提供了再加校验"，而是**根本不存在**。模型不能调用不存在的函数——这是六条红线里成本最低的实现。

## 三、顺序约束：代码强制，不靠提示词

单据级状态机：

```
loaded ──list_fee_lines──▶ evidenced ──map + dup──▶ compared ──▶ drafted
```

`build_review_draft` 的四条硬前置（`ledger.gate_before_draft()` + 数据库二次校验）：

| # | 条件 | 违反时返回 |
|---|---|---|
| 1 | 已读单据与费用行 | `E5003` + `missing` 列表 |
| 2 | 每行都做过服务项映射 | `E5003`：`"××未做服务项映射"` |
| 3 | 已跑过查重 | `E5003`：`"尚未查重"` |
| 4 | 无证据的行**必须已登记为缺项** | `E5003`：`"第 N 行 … 缺证据且未登记"` |

第 4 条刻意放宽一格并写清了理由：
"无来源定位的结果视为无效"针对的是**结论**。一行完全没有凭证时，正确做法不是拒绝整张单，
而是把它作为缺项列进草稿——但**必须先登记**，否则草稿里会出现一条"看起来正常、其实没证据"的行，
那才是最危险的。

拒绝时返回结构化体，让模型能自我纠正而不是死循环：

```json
{ "ok": false, "code": "E5003",
  "message": "还不能生成草稿，请先补齐以下步骤",
  "missing": ["海运费 未做服务项映射（先调 map_service_item）", "尚未查重（先调 check_duplicates）"] }
```

## 四、三道防线

| 防线 | 机制 | 拦什么 |
|---|---|---|
| 一 | **工具根本不存在** | 付款、开票、确认、审批、删重复项 |
| 二 | **Ledger + Gatekeeper** | 跳步、无证据写入、草稿早产 |
| 三 | 系统提示词 | 语气与习惯性越界（模型"想帮忙"的时候） |

只有第三道：换个问法就可能绕过去。
只有前两道：模型频繁撞墙，体验很差。
三层配合才既安全又能用。

另外两个运行期硬限制（也在代码里）：

- 单次 run 工具调用上限 24 次，超了 `E5001` 并中止
- 同一工具 + 同一参数重复 3 次 → `E5005` 中止（防打转）
- 单个工具结果回灌上限 4000 字符（防一份 200 行的单据把上下文一次撑爆）

## 五、系统提示词

见 `project/app/core/agent/prompt.py`。要点：

1. 明确"你是取证与整理者，不是决策者"
2. 写入类工具前必须取得来源定位（文件 + 页码 + 字段）
3. 给出**固定作业顺序**，并注明"一次能处理多行的不要拆成多次——步数是有限的"
4. 列出必须转人工的五种情形
5. 禁止声称已确认 / 已审批 / 已付款

**为什么给固定顺序而不是让模型自由编排**

结算核对是确定性流程。让模型自由串工具，收益是"看起来智能"，代价是：
每份单据执行路径都不一样、出错无法复现、审计说不清。
本项目最不能接受的恰好是这三件事。所以模型的自由度只保留在 L1 的判断上
（映射候选是否合理、疑点该归哪一类、缺项怎么描述）。

## 六、数据模型（10 张表，`sql/agent_schema.sql`）

```
settlement ──┬─ settlement_version ── fee_line ──┬─ evidence ── voucher
             ├─ finding（追加式）                └─ （source locator 就挂在 evidence 上）
             └─ review_draft
agent_run ── tool_call（每次工具调用一行）
service_item（合同服务项字典）
```

三个关键约束：

| 约束 | 落地 |
|---|---|
| 一单只能有一个"当前版本" | `UNIQUE (settlement_id) WHERE superseded_by IS NULL` |
| 追加式留痕 | `finding` 触发器只允许改 `resolved_at / resolved_by`，其余列 UPDATE 直接报错 |
| 来源定位不可为空 | `evidence.page_no >= 1`；`record_finding` 的 `evidence_refs` 非空 |

金额一律 `numeric(18,6)`，跨币种存"原币 + 汇率 + 汇率日期 + 折算规则版本"。

## 七、实施记录

### 已验证（真实 DeepSeek + 云 PG + 虚构样本）

演示单据 `JS-2026-0318`：8 行费用、7 条证据、7 条合同服务项，刻意埋了四类问题
（跨币种重复 / 缺证据 / 映射失败 / 版本矛盾）。

**一次完整运行**：

```
get_settlement → list_fee_lines → get_evidence → map_service_item → check_duplicates
→ record_finding ×7（其中 1 次被 E5002 拒绝，模型自行修正）
→ build_review_draft
共 8 步、13 次工具调用、约 52 秒

草稿：needs_review，8 行，缺项 2 行，登记问题 5 条
```

**草稿结果**：

| 行 | 费用名称 | 金额 | 映射 | 置信度 | 证据 | 状态 |
|---|---|---|---|---|---|---|
| 1 | 市内运输费 | 1250 CNY | 市内运输费 | high | 1 | 正常 |
| 2 | 报关服务费 | 860 CNY | 报关代理费 | high | 1 | 正常 |
| 3 | 仓储服务费 | 2400 CNY | 仓储服务费 | high | 1 | 正常 |
| 4 | 码头操作费(THC) | 3200 CNY | 码头操作费(THC) | high | 1 | 正常 |
| 5 | 海运费 | 1200 USD | 海运费 | high | 1 | **有疑点** |
| 6 | 海运费用 | 8300 CNY | 海运费 | high | 1 | 正常 |
| 7 | 其他杂费 | 450 CNY | 无匹配 | low | 0 | **缺项** |
| 8 | 综合服务费包干 | 5600 CNY | 仓储服务费 | low | 1 | **缺项** |

**模型自主发现的问题（5 条）**

1. 第 5/6 行跨币种疑似重复：折算后金额差 2.6%、名称归一后相同、同日 → `high`（0.9）
2. 第 7 行无任何凭证 → 缺证据
3. 第 7 行无法映射（候选为空）
4. 第 8 行映射置信度仅 0.333（"包干"类费用对不上单一服务项）
5. **第 5 条是我没有埋的**：v1 已确认却被未确认的 v2 取代 → 版本有效期与确认状态矛盾
   （这正是"版本判定必须用两个条件"要防的情形，模型自己发现了）

**闸口验证（离线直调工具，不经模型）**

- 未读单据直接 `build_review_draft` → `E5003` + 3 条 missing
- 未登记缺项即生成草稿 → `E5003`：`"第 7 行 其他杂费 缺证据且未登记"`
- `record_finding` 传空 `evidence_refs` → `E5003`（硬约束 6 的落地点）
- 补齐后再次生成 → 成功，`needs_review`

### 踩到的四个坑（都已修，记下来避免重犯）

| 现象 | 根因 | 处理 |
|---|---|---|
| 8 行单据跑 24 次调用仍未出草稿 | 逐行 `get_evidence` + 逐行 `map_service_item` = 16 次 | 两个工具改**批量入参**，16 次降到 2 次；并在提示词里注明"不要拆成多次" |
| `list_fee_lines` 返回 0 行，模型转人工 | 版本对象里的 `id` 与 `settlement_id` 同名字段，模型拿错了 | 版本 id 改名 `version_id`；`list_fee_lines` 对传入 version_id 做容错解析 |
| 页面草稿表格空白但接口 200 | asyncpg 对 jsonb 列返回字符串，前端 `summary.lines` 取不到 | 接口层 `json.loads` |
| `/runs/latest` 被 `/runs/{run_id}` 匹配 | FastAPI 按声明顺序匹配 | `latest` 路由移到参数路由之前 |

## 八、已知边界（交付时要写进说明）

1. **服务项映射用的是字面匹配**（分词 + 重叠度 + 包含加分），不是向量。
   因为原型 `EMB_PROVIDER=mock`，向量是哈希出来的，语义能力为零；用真实 embedding + pgvector 后接口不变。
   代价：会出现"综合服务费包干 → 仓储服务费 0.333"这类不靠谱候选，靠 `need_human` 兜住。
2. **没有跨会话记忆**：每次 run 独立，不记得"上次这单核到哪"。
3. **查重只看同单据内**：跨单据的重复（同一笔费用在两个批次各报一次）未实现。
4. **模型单次 run 约 50 秒**：单据行数上百时需要改成分段核对 + 后台任务。
5. **`agent_run` / `tool_call` 只增不减**：没有清理策略，长期运行需要按月归档。
